# Line Network Model

This folder is the clean iteration area for the course-project model.

The goal is to stop mixing several historical experiments (`metro_plan_v3.py`
through `metro_plan_v11.py`) and instead keep one explicit optimization problem:

> Given a set of valuable candidate metro stations with coordinates, design a
> connected metro line/network under a total construction-length budget so that
> high-value station pairs are connected efficiently.

## Why this formulation

The literature notes point most directly to the OD demand capture family of
rapid-transit alignment models, especially the single-alignment trip coverage
idea from Laporte et al. For our CS240 version, we simplify aggressively:

- Station candidates are generated before network optimization.
- Candidate stations are based on population centers, job centers, fixed
  transport hubs, and large commercial centers.
- Each candidate station has a scalar value `v_i`, formed by summing the
  merged population, job, transport, and commercial values.
- Pairwise connection reward is larger when two high-value stations have a
  short path inside the selected metro network: `v_i * v_j / D^S_ij`.
- The output is a connected metro line/network over those candidate stations.
- The objective is a single scalar score, not a full multi-objective model.

This keeps the problem explainable and implementable while still matching the
literature's core structure: candidate stations, OD capture, route length, and a
combinatorial network-design algorithm.

## Mathematical model

Let `V` be the candidate station set generated by preprocessing. Each station
`i in V` has coordinate `p_i = (lon_i, lat_i)` and scalar value:

```text
v_i = population_value_i + job_value_i + transport_value_i + commercial_value_i.
```

Let `ell_ij` be the geographic construction length of candidate edge `(i,j)`.
The decision object is a set of metro lines:

```text
L = {L_1, L_2, ..., L_K}
```

Each line is an ordered station sequence. A line may be open, such as
`(s1, s2, ..., sm)`, or closed, such as `(s1, s2, ..., sm, s1)`. Therefore,
cycles are allowed. The selected network `S = (V_S, E_S)` is the union of all
stations and edges used by these lines.

For selected stations `i` and `j`, let `D^S_ij` be the shortest-path distance
between them inside the selected network `S`, computed as the sum of selected
edge lengths along the shortest path. If both stations are included in the same
connected planned line/network, their connection reward is:

```text
r_ij(S) = v_i * v_j / D^S_ij.
```

For a selected connected subnetwork `S = (V_S, E_S)`, the total reward is:

```text
R(S) = sum_{i<j, i,j in V_S} v_i * v_j / D^S_ij
```

To avoid unrealistic alignments with very sharp bends, the objective includes a
line-level turn-angle penalty. It is computed from consecutive triples on the
same ordered line, not from arbitrary adjacent edges in the union graph. The
turn angle is measured as `0` degrees for a straight continuation and larger
values for sharper turns. Closed lines evaluate triples cyclically across the
closing edge; open-line terminal stations do not contribute a turn angle. Only
turns larger than `theta_0` are penalized:

```text
P(L) = sum over lines L_k sum over triples (a,b,c) in L_k
       (max(0, theta_abc - theta_0) / 90)^2
```

The current implementation uses:

```text
theta_0 = 60 degrees
lambda = 120,000,000
```

The construction length is:

```text
L(S) = sum_{(i,j) in E_S} ell_ij.
```

Single objective:

```text
maximize  R(S) - lambda * P(L)
subject to L(S) <= B
           every selected edge belongs to at least one line
           every selected station appears on at least one line
           station spacing constraints hold for adjacent selected edges
```

For a single open line, the solution is a path. For a closed line or several
lines, the union network may contain cycles. In words: choose a set of open or
closed metro lines, connect valuable station pairs through short network paths,
avoid excessive turns along each line, and stay within a total line-length
budget.

## Baseline algorithm

`01_select_stations.py` implements candidate-station preprocessing:

1. Generate population centers from weighted KMeans over residential population
   points.
2. Generate job centers from weighted KMeans over estimated job destinations.
3. Add fixed transport centers from the configured hub list as high-value
   optional candidates.
4. Add fixed large commercial centers from the prepared commercial layer.
5. Merge centers within 1 km into final candidate stations `V`, using
   value-weighted centroids and summing value components.
6. Export the four intermediate center layers, final candidate stations, a CSV
   composition table, and SVG maps.

`run_baseline.py` implements classical constructive baselines from the
literature notes:

1. `required_mst`
   - if required hubs are enabled, this is the minimum-cost tree connecting
     them; otherwise it is a two-station high-value seed reference.
2. `greedy_value_tree`
   - prize/value-collecting tree heuristic.
   - Start from the configured seed and repeatedly attach the station
     with the largest reward-density to the current connected network.

All methods use the same network-shortest-path reward `v_i * v_j / D^S_ij`, turn penalty, and
length budget. The comparison table reports the raw `pair_reward`,
`turn_penalty`, `max_turn_deg`, and final `objective_score`. The script exports:

- `output/05_baseline_comparison.csv`
  - summary table for all baselines
- `output/04_baseline_<method>.svg`
  - visual map for each method
- `output/04_baseline_line.svg`
  - compatibility copy of the best-by-score baseline
